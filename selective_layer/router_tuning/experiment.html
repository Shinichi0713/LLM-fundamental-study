    実験

    実際に実施する実験の内容について説明していきます。

    1. 実験の意図は何か

    LLMは文章を生成する際、すべての層を毎回通すため計算コストが高く、応答が遅くなります。そこで 「重要でない計算を省略して速くする」 手法として Router-Tuning があります。

    しかし、本当に

    • モデルの本体を一切触らずに、
    • わずか数分〜数十分の学習で、
    • 精度をほぼ落とさずに、
    • 実際の処理速度が上がるのか？

    ということを、Google Colabeでも実行可能な小さなモデル（Qwen2.5-0.5B）を使って再現・確認するのがこの実験の目的です。

    2. 実験設定

    実験は 5つのステップ で進めていきます。

    ① モデル準備と凍結 Qwen2.5-0.5B（5億パラメータの言語モデル）を読み込み、すべての重みを固定（凍結） します。これは「本体は絶対に壊さない」という Router-Tuning の基本方針です。

    ② どの Attention 層を飛ばせるかを分析 各 Transformer 層について、「Attention を通す前と後の表現がどれくらい似ているか」をコサイン類似度で測ります。似ていれば「この層の Attention はほとんど変化を起こしていない＝冗長＝飛ばしても大丈夫」 と判断し、飛ばし候補の層を 12 層選びます。

    ③ ルーターの取り付けと学習 選ばれた 12 層の Attention の手前に、「この層は必要か？」を判断する小さなルーター（単層の線形変換） を付けます。このルーターだけを 300 ステップ、小さなデータ（Wikitext）で学習します。学習時は「文章の予測精度を保ちつつ、できるだけ Attention を省略するように」と教えます。

    ④ 精度の検証 学習したルーターが本当に良い判断をしているか、以下で確認します。

    • Perplexity（文章の予測しやすさ）: 数値が低いほど文章を正しく予測できている
    • ARC-Easy（小中学生向け科学問題）: ゼロショットで正解率を測定
    • 静的ベースラインとの比較: 同じ数の層を「固定で」飛ばした場合と比較

    ⑤ 速度の検証 実際に処理が速くなったかを測定します。

    • Prefill: 長い文章を一度に処理する時間（256/1024/2048 トークン）
    • Decode: 新しい文章を 128 トークン生成するスループット

    3. 実験の問題設定

    実験を実施した条件について整理しました。 実行環境はGoogle Colabです。

    項目 設定値 意味
    モデル Qwen/Qwen2.5-0.5B 小規模な言語モデル（実験用）
    総層数 24 層 うち 12 層を飛ばし候補に
    飛ばし目標 候補 12 層のうち半分（50%） つまり平均して 6 層の Attention を省略
    ルーターが見る範囲 先頭 64 トークン 文章の最初の部分だけ見て判断
    学習データ Wikitext-2（小規模な Wikipedia データ） 300 ステップ、バッチサイズ 8
    学習対象 ルーターの重みのみ（約 0.01%） モデル本体は一切更新しない
    判断のしきい値 τ 0.2〜0.8 で変化させて検証 τ が高いほど「飛ばし」が増える

    表下に設定した τ は「Attention層を実行するかスキップするか」の境界線を決める 0〜1 のしきい値です。

    実装は以下の2ステップです。

    1. スコアの計算: ルーター（単層の線形変換）が、入力の先頭 64 トークンの平均表現から 0〜1 のスコア s を sigmoid で出力します。
    2. しきい値判定: s >= τ なら「この層を実行」、s < τ なら「スキップ」と二値化します。

    τ の値で挙動が変わります。

    τ の値 意味 実行される層の割合 精度 速度
    低い（0.2） 緩い判定 多い 高い 速くなりにくい
    高い（0.8） 厳しい判定 少ない 低い 速くなりやすい

    つまり、τ は「速度と精度のトレードオフ」を手動で調整するダイヤルのようなパラメータです。学習中は τ=0.5 で固定し、推論時に τ を変えることで「どれだけ積極的に層を飛ばすか」を制御します。

    4. 期待する出力

    実験が成功すると、以下のような結果が得られるはずです。

    精度面

    • ルーター適用後の perplexity が、「同じ数の層を固定で飛ばした場合」よりも良い
    • ベースライン（全層通過）との差が小さい（論文では 0.2% 程度の低下）

    これが確認できれば、「ルーターが賢く『この入力ではこの層は不要』と判断できている」ことの証拠になります。

    速度面

    • Prefill 時間が短縮される（特に長い文章ほど効果が大きい）
    • Decode スループットが向上する（1 秒間に生成できるトークン数が増える）

    トレードオフの可視化 しきい値 τ を変える実験で、以下の関係が確認できます。

    • τ を上げる（厳しく飛ばす）→ 速くなるが、perplexity が悪化（精度低下）
    • τ を下げる（保守的に飛ばす）→ 精度は保たれるが、速度向上が小さい

    この「速度と精度のトレードオフ曲線」が描ければ、実験は成功です。

    層ごとの実行率 各候補層の「実際に実行された割合」が、0 か 1 に張り付いているか、それとも中間的な値かを確認できます。

    • 0 か 1 に張り付く → 実質的に「この層は常に飛ばす/常に通す」という静的な判断を学習しただけ
    • 入力によって変わる → 本当に動的な判断ができている

    実装

    今回実験の実装について要点となることを説明していきます。 一言でいうのであれば、モデル本体は一切触らず、既存の Attention 層の forward を差し替えるだけで動的スキップを実現するという実装です。

    1. Router（ルーター）の実装

    ルーターは 「各 Attention 層の手前に置く、超軽量な判断機構」 です。

    # 各スキップ候補層に 1 つずつ
self.routers = nn.ModuleDict({
    str(i): nn.Linear(d_model, 1)  # 入力: 隠れ状態, 出力: 1次元のスコア
    for i in self.skip_layers
})

    動作の流れは以下の通りです。

    1. 入力の集約: 文章の先頭 PREFIX_LEN（64）トークンの隠れ状態を平均し、1 つのベクトルに圧縮
    2. 正規化: LayerNorm でスケールを統一
    3. スコア化: 単層の線形変換 → sigmoid で 0〜1 のスコア s を出力
    4. 判定: s >= τ なら実行（1）、s < τ ならスキップ（0）
    def score(self, i, hs):
    p = hs[:, :self.prefix_len].float().mean(1)   # [B, D] プロンプト平均
    p = F.layer_norm(p, p.shape[-1:])             # 正規化
    return torch.sigmoid(self.routers[str(i)](p))  # [B, 1] 0〜1のスコア

    初期化の工夫も重要です。バイアスを 1.0 に設定することで、学習開始時は sigmoid(1.0)≈0.73 となり、τ=0.5 では最初は全層を実行する状態から始まります。これにより、学習初期からモデルが壊れるのを防ぎます。

    2. MindSkip クラス：層の forward を差し替える

    これが本実装の最大の特徴です。モデルの構造を変更するのではなく、既存の self_attn.forward を実行時に書き換え（monkey patching） ます。

    # 元の forward を保存
self.orig[i] = self.layers[i].self_attn.forward

# 新しい forward に差し替え
self.layers[i].self_attn.forward = self._make(i)

    これにより、既存の学習済みモデルに対して後付けで動的スキップを導入できます。

    3. 4つの動作モード

    差し替えた forward は、モードに応じて異なる動作をします。

    モード 動作 用途
    off 元の Attention をそのまま実行 ベースライン測定
    route ルーターのスコアで 0/1 ゲートを掛ける（計算は省略しない） 学習・perplexity 評価
    skip ルーターの判断に従い、Attention 計算自体を省略（バッチサイズ 1 専用） 速度計測・生成
    static 指定した層を常にスキップ 比較用ベースライン

    route と skip の違いが重要です。

    • route は「Attention は計算するが、出力に 0 を掛けて無効化」（勾配計算が必要なため）
    • skip は「Attention 計算を丸ごと飛ばす」（実際の速度向上を測るため）

    4. Straight-Through Estimator

    sigmoid(x) >= τ の判定は微分不可能です。これを学習可能にするのが以下の実装です。

    hard = (s >= self.tau).float()           # 順伝播: 0 か 1 のハードな値
if self.train_gate:
    g = hard + s - s.detach()           # Straight-Through Estimator
    • detach() で勾配を止め、ソフトな s の値をそのまま流す
    • 順伝播では hard（0/1）を使い、逆伝播では s（0〜1の連続値）の勾配を流す
    • これにより、ルーターのパラメータを通常の勾配法で学習できる

    5. 損失関数：LM 損失 + 容量損失

    ルーターだけを学習する際、「精度を保ちつつ、目標の割合だけ層を飛ばす」 ように教えます。

    lm = F.cross_entropy(...)                          # 文章予測の損失
exec_frac = torch.stack([g.mean() for g in ms.gates.values()]).mean()
loss = lm + CAP_LAMBDA * (exec_frac - TARGET_CAPACITY) ** 2
    • LM 損失: 文章を正しく予測できるか（精度を保つ）
    • 容量損失: 実際の実行割合 exec_frac が目標 TARGET_CAPACITY（0.5）から離れるとペナルティ
    • CAP_LAMBDA（5.0）でペナルティの強さを調整

    6. 冗長性分析：どの層を飛ばし候補にするか

    全層を飛ばし候補にするのは非効率です。そこで 「Attention の寄与が小さい層さい層＝冗長な層」 をコサイン類似度で選定します。

    # Attention の入力 x と、出力 x+Attn(x) の類似度を測定
sim = F.cosine_similarity(x, x + attn_out)  # 高いほど冗長（変化が小さい）

    類似度が高い層ほど「Attention を通しても表現がほとんど変わらない＝飛ばしても大丈夫」なので、スキップ候補に選びます。

    7. 評価の実装上の重要点

    Perplexity 測定の注意

    • 先頭 64 トークンを「プロンプト」としてルーターに見せ、その後ろのトークンだけで perplexity を測定
    • これにより「ルーターが未来のトークンを見て判断する」という情報漏れを防ぐ

    ARC-Easy 評価

    • 各選択肢の対数尤度で回答を選択（acc_norm は文字数で正規化）
    • ルーターは質問文の先頭トークンだけ見て判断し、選択肢のトークンは見ない
    • これも情報漏れ防止のため

    速度計測

    • skip モードで実際に Attention 計算を省略
    • ルーターの判断コスト（先頭 64 トークンの平均計算 + 線形変換）も計測に含める
    • これにより「理論上の FLOPs 削減」ではなく「実際の速さ」を測定

    実装全体のまとめ

    既存モデルを読み込み → 全パラメータを凍結
        ↓
各層の Attention 冗長性をコサイン類似度で分析 → 飛ばし候補 12 層を選定
        ↓
候補層の self_attn.forward を差し替え（monkey patching）
        ↓
ルーター（単層線形）を追加 → 初期バイアス 1.0 で「全層実行」から開始
        ↓
学習: LM損失 + 容量損失 でルーターのみ 300 ステップ学習
        ↓
推論: τ を変えながら perplexity・速度・ARC精度を評価

    実験結果

    結論から言うと、今回の設定では 「精度は維持できておらず、速度向上も確認できない」 という結果でした。 今回の結果のみから論文の主張を否定することはできず、実験の設定がまだ手法の効果が出る条件に達していない可能性を考えています。

    結果の全体像

    指標 Baseline Router Static
    Perplexity 14.04 18.59 17.01
    ARC-Easy 精度 0.56 0.57 0.53
    Prefill 1024 加速 1.00× 1.04× 1.06×
    Decode 加速 1.00× 1.03× 1.05×

    ポイント1：速度は向上しているが、効果は限定的

    • Prefill（1024トークン）: Router で 4%、Static で 6% の加速
    • Decode（生成）: Router で 3%、Static で 5% の加速

    Static（固定で層を飛ばす）の方が一貫して速い結果になっています。これは Router の判断にコストがかかるためです。

    ポイント2：Router が非常に保守的（飛ばしが少ない）

    「ルーターが実行した Attention 層数：22/24層」

    つまり、24層中わずか2層しか飛ばしていません。論文の設定では「候補12層のうち半分（6層）を飛ばす」が目標でしたが、実際にはほとんど飛ばしていない状態です。

    これが速度向上が限定的（3〜4%）な原因です。

    ポイント3：Perplexity の劣化が大きい

    方法 PPL Baseline からの変化
    Baseline 14.04 —
    Router 18.59 +32% 悪化
    Static 17.01 +21% 悪化

    論文では「性能低下わずか0.2%」と報告されていますが、この実験では Perplexity が大幅に悪化しています。これにはいくつかの理由が考えられます。

    • モデルサイズ: 論文は Llama-3（8B）など大きなモデルで検証。0.5B の小さなモデルでは層の冗長性が少なく、飛ばすと壊れやすい
    • 学習不足: 300 ステップ・小さなデータではルーターが十分に学習できていない可能性
    • τ=0.5 の設定: 初期バイアス 1.0 のままでは sigmoid(1.0)≈0.73 で、τ=0.5 なら「ほぼ全層実行」になってしまう

    ポイント4：ARC-Easy 精度は意外と健闘

    方法 ARC-Easy 正解率
    Baseline 0.56
    Router 0.57 ← わずかに上回る
    Static 0.53

    Perplexity は大きく悪化していますが、多肢選択タスク（ARC-Easy）では Router が Baseline をわずかに上回る結果が出ています。これは「ルーターが不要な計算を省き、本質的な判断に集中できた」可能性もありますが、誤差の範囲とも言えます。

    ポイント5：生成トークンの一致率が極めて低い

    token_match_vs_base = 0.047（約5%）

    Baseline と比較して、生成されたトークンの一致率が 約5% しかありません。これはモデルの振る舞いが大きく変わっていることを示しています。

    結論：この実験で示されたこと

    • 実装は正しく動作している（ルーターが判断し、層をスキップしている）
    • 速度はわずかに向上（3〜6%）
    • スキップする層が少なすぎる（目標6層に対し実際2層）
    • Perplexity が大幅に悪化（論文の結果とは大きく異なる）
    • 生成結果が Baseline と大きく異なる（一致率5%）

    事後アクションの検討

    今回結果を受けて次に行うべきアクションについて検討しました。

    1. 容量を目標に近づける: CAP_LAMBDA を 20〜50 に上げる、MAX_STEPS を増やす、LR を上げる。それでも exec が 0.5 に届かなければ、τ を上げて実行割合を下げられるかを見ます。
    2. ルータの価値を確認する: 層ごとの exec_rate の表を見てください。全層が 0 か 1 に張り付いていれば、入力依存の判断はなく、静的な選択と同じです。学習データが wikitext だけだと入力が似通っているので、コード・数学・Wikipedia などを混ぜるとルータが働く余地が出ます。
    3. 評価の精度を上げる: ARC は問題数を増やす（500以上）か、HellaSwag など別タスクを加えます。
    4. 速度の測り方を改善する: ベースラインと各方式を交互に何度も測って中央値を取る、reps を増やす、2層スキップではなく6層程度のスキップで測る、といった対応が必要です。
    5. 条件を変える: decode のコスト中の Attention の割合は、モデルが大きいほど、またコンテキストが長いほど増えます。1.5B〜3B 級のモデルと、2k〜8k トークンの長い文脈で decode を測ると、Attention 層をスキップする効果が見えやすくなります。

    総括

    結論: 今回の実験では、Router-Tuning の論文で報告されたような「精度を保ちつつ大幅に高速化する」効果は確認できませんでした。

    実験結果のエッセンス

    指標 結果
    速度向上 わずか 3〜6%。Static（固定スキップ）の方が一貫して速い
    スキップ層数 目標 6 層に対し、実際はわずか 2 層のみ（極めて保守的）
    Perplexity Baseline 14.04 → Router 18.59（+32% 悪化）
    ARC-Easy 精度 Baseline 0.56 → Router 0.57（同等〜わずかに上回る）
    生成一致率 Baseline との一致率 約 5%（振る舞いが大きく変化）

    所感

    実装は正しく動作し、ルーターが動的に判断していること自体は確認できました。しかし、「飛ばす層が少なすぎて速度効果が限定的」 かつ 「Perplexity が大幅に劣化」 という結果となり、論文の主張とは大きく異なる outcome でした。

    この乖離の主な原因として、① 0.5B モデルでは層の冗長性が不足、② 300 ステップ・小データでは学習が不十分、③ τ=0.5 の設定では飛ばしが起きにくい、の 3 点が考えられます。つまり、「手法自体は動いたが、効果が出る条件（モデル規模・学習量・ハイパーパラメータ）に達していなかった」 と総括できます。
